Unityからの移行

Unityでプロジェクトを作ったことがあれば、PlayCanvasの多くはなじみのあるものに感じられるはずです。PlayCanvas Editorには、ヒエラルキー、インスペクター、アセットパネル、3Dビューポートがあります。シーンはエンティティのツリーで、エンティティはコンポーネントで構成され、振る舞いはinitializeやupdateなどのライフサイクルメソッドを持つスクリプトで記述します。

このガイドでは、Unityで身につけた知識をPlayCanvasに対応付けます。エディターのパネルとショートカット、共通する概念の名前、C#のAPIとそれに相当するJavaScript、そしてPlayCanvasの動作が異なる点を取り上げます。各セクションから、そのトピックの詳しいドキュメントにリンクしています。

主な違い​

  • すべてがブラウザーで動作します。 エディターはWebアプリケーションで、プロジェクトはオンラインに保存され、公開するものもWebアプリです。WebGLのビルドを待つ必要はありません。アプリは、エディターのビューポートと同じエンジンで動作します。
  • スクリプトはJavaScriptで書きます。 スクリプトはC#のクラスではなくJavaScriptのモジュールとして書きます。コンパイルは不要で、スクリプトを保存したらそのまま起動できます。
  • スクリプトは1つのコンポーネントを共有します。 Unityでは、MonoBehaviourのそれぞれが独立したコンポーネントです。PlayCanvasでは、エンティティに1つのScriptコンポーネントがあり、そのエンティティのすべてのスクリプトを保持します。
  • 各タイプのコンポーネントはエンティティごとに1つです。 エンティティが持てるカメラ、ライト、Collisionコンポーネントなどはそれぞれ1つで、各スクリプトも1回しか追加できません。コライダーを2つ使いたい場合など、同じものが2つ必要なときは子エンティティを使います。
  • 座標系は右手系です。 前方は+Zではなく-Zです。座標系と単位を参照してください。
  • Playモードはありません。 シーンを起動すると、エディターに接続されたままの別のブラウザータブで実行されます。
  • コラボレーションとバージョン管理が組み込まれています。 複数の人が同じシーンを同時に編集でき、チェックポイント、ブランチ、マージはエディターの機能です。

Playモードの代わりに起動する​

Unityはゲームをエディターの中で再生します。PlayCanvasは新しいブラウザータブで起動ページを開き、公開したときと同じようにシーンを実行します。Launch をクリックするか、Ctrl+Enterを押してください。

起動ページはエディターに接続されたままです。エンティティ、コンポーネント、スクリプト属性、アセット、シーン設定への変更は、加えたそばから実行中のアプリに反映されます。Playモード中の編集とは違い、停止しても変更は失われません。エディターはすべての変更をその都度保存するからです。この使い方をするには、2つのタブを横に並べて配置してください。コードの変更は、スクリプトがホットリロードに対応していない限り、再読み込みが必要です。

スクリプトがエディターのビューポートで実行されることはないため、Unityの[ExecuteInEditMode]に相当するものはありません。スクリプトが作成したり変更したりするものは、起動したアプリにしか現れません。

Launchボタンのメニューには、テスト用のオプションがあります。グラフィックスAPIを選んだり、プロファイラー、MiniStats、Inspectorを開いたりできます。Debug にチェックを入れると、エンジンの警告とエラーがコンソールに記録されます。

座標系と単位​

どちらのエンジンもYを上方向とし、距離をメートル、角度を度で扱います。違いは座標系の向きです。Unityの座標系は+Zが前方の左手系ですが、PlayCanvasは -Zが前方 の右手系です。カメラは自身の負のZ軸の方向を向き、entity.forwardは負のZ軸を返し、lookAtは負のZ軸をターゲットに向けます。

このため、コードやコンテンツを移植するときには、次の点に注意が必要です。

  • 前進は-Z方向への移動です。 transform.Translate(0, 0, speed * Time.deltaTime)はthis.entity.translateLocal(0, 0, -this.speed * dt)になります。
  • 正の回転の向きが逆になります。 Y軸まわりの正の回転はエンティティを左に向け（上から見て反時計回り）、X軸まわりの正の回転は上に傾けます。Unityではそれぞれ右と下に回るため、シーンを見下ろすカメラのX回転は、PlayCanvasでは負の値になります。
  • オイラー角を適用する順序が異なります。 PlayCanvasはX、Y、Zの順に回転を適用しますが、UnityはZ、X、Yの順に適用します。軸の向きの反転と合わせて考えると、UnityのInspectorで読み取った回転の値はそのままでは使えません。レイアウトは、変換を行ってくれるエクスポートファイルで移行してください。コンテンツの移行を参照してください。
  • ライトは-Y方向を照らします。 ディレクショナルライトとスポットライトはローカルの負のY軸の方向を向くため、回転していないライトは真下を照らします。Unityでは+Z方向を照らします。
  • モデルは通常+Zを向いています。 glTFは+Zをモデルの正面と定めており、Unityからエクスポートしたモデルも+Zを向いたままです。これはPlayCanvasでは後ろ向きになります。スクリプトでキャラクターをentity.forwardの方向に動かす場合は、モデルを親エンティティの中に入れてY軸まわりに180°回転させ、モデルが親の前方を向くようにします。
  • デフォルトの視野角が狭くなっています。 どちらのエンジンも視野角を垂直方向で測りますが、PlayCanvasの新しいカメラは60°ではなく45°から始まります。

スクリプト​

PlayCanvasのスクリプトは、Scriptを継承するJavaScriptのクラスです。各スクリプトはアセットパネル内の.mjsファイルにあり、エンティティにScriptコンポーネントを追加してスクリプトを選ぶとアタッチできます。詳しくはスクリプティングを参照してください。

スクリプトの比較​

次のUnityスクリプトは、GameObjectを回転させ、スペースキーでライトのオンとオフを切り替えます。

using UnityEngine;

public class Spinner : MonoBehaviour
{
    // 1秒あたりの回転角度（度）
    [SerializeField] float speed = 90f;
    [SerializeField] Light lamp;

    void Start()
    {
        lamp.enabled = false;
    }

    void Update()
    {
        transform.Rotate(0f, speed * Time.deltaTime, 0f);

        if (Input.GetKeyDown(KeyCode.Space))
        {
            lamp.enabled = !lamp.enabled;
            Debug.Log($"Lamp on: {lamp.enabled}");
        }
    }
}

同じスクリプトをPlayCanvas用にspinner.mjsというファイルで書くと、次のようになります。

import { Entity, KEY_SPACE, Script } from 'playcanvas';

export class Spinner extends Script {
    static scriptName = 'spinner';

    /**
     * 1秒あたりの回転角度（度）。
     *
     * @attribute
     */
    speed = 90;

    /**
     * @attribute
     * @type {Entity}
     */
    lamp;

    initialize() {
        this.lamp.light.enabled = false;
    }

    update(dt) {
        this.entity.rotateLocal(0, this.speed * dt, 0);

        if (this.app.keyboard.wasPressed(KEY_SPACE)) {
            this.lamp.light.enabled = !this.lamp.light.enabled;
            console.log(`Lamp on: ${this.lamp.light.enabled}`);
        }
    }
}

注目すべき違いは、次のとおりです。

  • scriptNameがスクリプトの名前になります。 エディターはこの名前でスクリプトを表示し、他のスクリプトはこの名前でスクリプトにアクセスします（entity.script.spinner）。
  • [SerializeField]の代わりに@attributeを使います。 JSDocコメントで@attributeタグを付けたクラスフィールドがインスペクターに表示され、コメントの最初の文がフィールドのツールチップになります。インスペクターのフィールドを参照してください。
  • Entity属性は、コンポーネントではなくエンティティを参照します。 Entity型の属性はエンティティを保持するので、this.lamp.lightのように、そのエンティティを通じてコンポーネントにアクセスします。
  • this.entityはGameObjectとそのTransformに相当します。 this.appはアプリケーションで、入力デバイス、シーンの階層（this.app.root）、アセットレジストリなどにアクセスできます。
  • dtはTime.deltaTimeに相当します。 エンジンは、フレーム時間を秒単位でupdateに渡します。

ベクトルはオブジェクトです​

UnityのVector3とQuaternionは構造体で、代入するたびにコピーされます。PlayCanvasのVec3とQuatはクラスなので、代入すると1つのオブジェクトを共有します。また、JavaScriptには演算子のオーバーロードがありません。このため、次の3つを習慣にしてください。

  • 返されたベクトルは読み取り専用として扱います。 entity.getPosition()などのゲッターは、エンティティが所有して再利用するベクトルを返します。その値はエンティティが動くと変わり、書き込んでもエンティティは正しく更新されません。値を保持するにはclone()を呼び、値を変えるにはsetPosition()などのセッターを使います。
  • 演算子の代わりにメソッドを使います。 add、sub、mulScalarなどのメソッドは、呼び出したベクトル自体を変更して、そのベクトルを返します。add2(a, b)などのメソッドは、呼び出したベクトルに結果を書き込みます。
  • update内でのアロケーションを避けます。 毎フレームベクトルを作成すると、ガベージコレクターの負担が増え、カクつきの原因になります。一度だけ作成して再利用してください。
import { Script, Vec3 } from 'playcanvas';

export class Mover extends Script {
    static scriptName = 'mover';

    /** @attribute */
    speed = 5;

    // 一度だけ作成し、毎フレーム再利用する
    step = new Vec3();

    update(dt) {
        // Unity: transform.position += transform.forward * speed * Time.deltaTime;
        this.step.copy(this.entity.forward).mulScalar(this.speed * dt);
        this.entity.translate(this.step);
    }
}

イベントとメッセージ​

C#のイベント、UnityEvent、SendMessageは、いずれもPlayCanvasのイベントに対応します。アプリケーション、エンティティ、スクリプトは、イベントを発火したりリッスンしたりできます。

// どこからでも: アプリケーションでイベントを発火する
this.app.fire('player:died', this.entity);

// 別のスクリプトで: イベントをリッスンし、スクリプトが破棄されたらリッスンをやめる
initialize() {
    this.app.on('player:died', this.onPlayerDied, this);
    this.once('destroy', () => {
        this.app.off('player:died', this.onPlayerDied, this);
    });
}

他のオブジェクトに追加したリスナーは、スクリプトが破棄されるときに必ず削除してください。削除しないと、リスナーが動き続け、スクリプトもメモリに残ります。

コルーチンとタイマー​

PlayCanvasにはコルーチンやInvokeはありません。ゲームプレイのタイマーは、updateでカウントダウンしてください。こうすると、タイマーはapp.timeScaleに従い、スクリプトが無効な間は止まり、エンティティが破棄されると終了します。

// Unity: Invoke(nameof(Spawn), 2f);
initialize() {
    this.spawnTimer = 2;
}

update(dt) {
    if (this.spawnTimer > 0) {
        this.spawnTimer -= dt;
        if (this.spawnTimer <= 0) {
            this.spawn();
        }
    }
}

ブラウザーのsetTimeout、setInterval、awaitを使うasync関数は、読み込みなど、ゲーム内の時間に結びつかない処理に便利です。ただし、実時間で動き、スクリプトが破棄された後も動き続けるため、destroyハンドラーでキャンセルしてください。

実行順序​

同じエンティティ上のスクリプトは、Scriptコンポーネントに並んでいる順に実行されます。この順序はドラッグで変更できます。UnityのScript Execution Order設定のようにエンティティ間の順序に頼るのではなく、postInitializeとpostUpdate、またはイベントを使ってください。

コードの共有とパッケージの利用​

スクリプトはESモジュールなので、importとexportでコードを共有します。モジュールのトップレベルの変数は、そのモジュールをインポートするすべてのスクリプトで共有されるため、C#で静的クラスやシングルトンとして書くものは、モジュールに置くのが適しています。モジュールはシーンを切り替えても残ります。

エディターでnpmのパッケージを使うには、インポートマップでパッケージ名をCDNのURLに対応付けます。エディターを使わずに作るプロジェクトでは、他のWebプロジェクトと同じように、npmからパッケージをインストールします。

Unityの開発者の多くが、次の違いでつまずきます。

  • 静的なコライダーにもRigid Bodyが必要です。 Collisionコンポーネントだけではトリガーボリュームになり、ボディを検出しますが、止めることはしません。床や壁には、StaticタイプのRigid Bodyコンポーネントを追加してください。
  • プリミティブのコリジョン形状はスケールを無視します。 ボックス、球、カプセルの形状は、エンティティをどうスケールしてもHalf ExtentsやRadiusのままです。例外はメッシュ形状です。スケールを参照してください。
  • FixedUpdateはありません。 シミュレーションは1秒に60回の固定レートでステップし、力はupdateから加えます。衝突イベントは、物理ステップごとに1回発生します。
  • Dynamicなボディは物理エンジンが所有します。 各ステップの後、エンジンはすべてのDynamicなボディの位置と回転をそのエンティティに書き込みます。そのため、Dynamicなボディは、エンティティのトランスフォームを設定するのではなく、力、速度、teleportで動かします。

コンテンツの移行​

Unityのプロジェクトを自動で変換するツールはありません。アセットは標準的なファイル形式で移行し、コードは書き直します。

  • モデルとアニメーション。 UnityGLTFやUnityのglTFastパッケージなどのglTFエクスポーターでGLBファイルとして、またはUnityのFBX ExporterパッケージでFBXとしてエクスポートします。エディターがインポートするのはglTFのバイナリ形式である.glbで、.gltfではありません。ファイルをアセットパネルにドラッグすると、FBXファイルはGLBに変換され、各モデルからRender、マテリアル、テクスチャ、アニメーションのアセットと、その階層のテンプレートが作成されます。3Dモデルのインポートを参照してください。
  • マテリアル。 Unityのシェーダーは移行できません。glTFエクスポーターはStandardやURP LitのマテリアルをglTFのPBRマテリアルに変換し、それがPlayCanvasのマテリアルとしてインポートされます。FBXファイルが持つマテリアルの情報は少ないため、FBXのマテリアルは設定し直すことになります。
  • テクスチャ、オーディオ、フォント。 元のファイルをアップロードします。サポートされているフォーマットを参照してください。
  • シーンとPrefab。 シーンの静的なジオメトリを1つのGLBとしてエクスポートしてレイアウトを保ち、ライト、カメラ、物理演算、UI、スクリプトはエディターで追加します。
  • Terrain。 エクスポートする前に、Terrainをメッシュに変換します。
  • スクリプトとシェーダー。 JavaScriptと、GLSLまたはWGSLで書き直します。AIコーディングアシスタントは、MonoBehaviourの変換を得意としています。エディターのプロジェクトのスクリプトをアシスタントに扱わせるには、VS Code拡張機能でスクリプトを同期します。シーンも編集させる場合は、MCPサーバーでエディターに接続します。
  • ライトマップ。 PlayCanvasのライトマッパーでベイクし直すか、3Dモデリングツールでベイクしてモデルと一緒にインポートします。

公開​

Unityはプラットフォームごとにプレイヤーをビルドします。PlayCanvasが公開するのは、HTML、JavaScript、アセットで構成されるWebアプリです。

  • Publish はビルドをPlayCanvasでホストし、共有用のURLを発行します。PlayCanvasホスティングを参照してください。
  • Download は、セルフホスティング用のZIPファイルを作成します。
  • アプリストア向けには、Webアプリをモバイルやデスクトップ向けにラップするか、プレイアブル広告として公開します。

Unityのプロジェクトは、自分でバージョン管理の下に置くフォルダーです。PlayCanvasのプロジェクトはオンラインで共有されます。チームメンバーが同じシーンを開くと、リアルタイムで一緒に編集でき、互いの変更をその場で確認できます。履歴はエディターのバージョン管理で管理します。コミットのようにチェックポイントを作成し、ブランチで作業し、競合を解決しながらマージします。

組み込みの機能がないもの​

UnityPlayCanvasでの代替手段
Terrain地形をメッシュとしてインポート
NavMeshとAI NavigationPlayCanvasに対応したrecast-navigation-jsなどのライブラリ
Character Controllerスクリプトで動かすDynamicなRigid Body、またはエンジンの一人称・三人称コントローラースクリプト
2D物理Linear FactorとAngular Factorで3つ目の軸を固定した3D物理
TimelineとCinemachineアニメーションさせる値にCurve属性を使うスクリプト
VFX GraphParticle Systemコンポーネント
Light Probeとリアルタイムのグローバルイルミネーションライトマップと環境ライティング
DOTweenなどのトゥイーンパッケージCDNからインポートするJavaScriptのトゥイーンライブラリ
